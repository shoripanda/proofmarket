# Owner A: let any AI request "without signing up" through x402

Branch: `feat/x402` / worktree: `../Solana-idea-a` / DB migration number: 0019 (only if needed)

## Why
Today nobody can request until the operator issues an API key by hand. With x402, an AI agent can request with no contract or sign-up just by paying USDC from its own Solana wallet. It is the decisive answer to the judges' question "can other AIs use this?", and it makes the reason for using Solana clear. At Colosseum, payment rails for AI (Latinum, MCPay, Corbits) have placed one after another.

## What to build
1. **The x402 endpoint** `POST /v1/x402/verifications`
   - The body is the same as `POST /v1/verifications`, except `principal_ref` is not needed.
   - Without a payment, return HTTP 402 with the payment requirements. The amount is `bounty.amount × required_witnesses` (in USDC base units).
   - With a payment attached, verify it, send it to Solana, wait for confirmation, then create the request. The response has the same shape as a normal create, plus:
     - an API key for that paying wallet (to read results with `GET /v1/verifications/{id}`)
     - the payment transaction's signature and Explorer URL
   - Create one principal per paying wallet (display name `x402:<start of pubkey>`), reused from the second time on. A new API key may be issued every time (a secret can only be returned once).
   - Book the amount received as a TOPUP in the ledger and RESERVE from it as usual; that is, reuse `createVerification` as is.
   - Idempotency: one payment (transaction signature) must never create two requests.
2. **Verifying and sending the payment (our own facilitator)**
   - Follow the latest coinbase/x402 spec. The Solana "exact" scheme: https://github.com/coinbase/x402/blob/main/specs/schemes/exact/scheme_exact_svm.md . Decide the header names (v1's `X-PAYMENT` / `X-PAYMENT-RESPONSE`, v2's names) after checking the spec in that repository. If an official npm package provides Solana verification, it may be used; otherwise write it.
   - Verify every MUST in the spec: instruction layout (two Compute Budget instructions + TransferChecked, optional Memo), the fee payer is neither the transfer source nor its authority, a cap on the compute unit price, the destination is `payTo`'s ATA, the amount matches exactly, the mint is `BOUNTY_MINT`.
   - `payTo` is the operator's wallet (owner of the treasury that funds escrow; see `packages/solana/src/anchor-adapter.ts`). The fee payer (`extra.feePayer`) is also the operator's key.
   - The network is Solana Devnet (CAIP-2 identifier per the spec). In production, reuse the existing check of `SOLANA_EXPECTED_GENESIS_HASH`.
3. **A sample agent that pays and requests** `scripts/x402-agent.ts`
   - With its own Devnet wallet (key at `~/.config/proofmarket/x402-agent.json`, created if missing), it receives the 402, builds and partially signs the payment transaction, resends to create the request, waits for the result and prints it.
   - Explain in the README or at the end of the instructions how to put test USDC in the wallet (Circle's faucet, or a script sending a small amount from the operator's treasury).
4. **Usable from MCP too** (if time allows): add one sentence to the MCP tool descriptions pointing to the x402 endpoint. No payment support in MCP itself.
5. **The site's developer page** (`apps/web/app/(site)/developers/page.tsx`): add a "Use without signing up (x402)" section, with the curl-equivalent flow and how to use the sample agent.
6. **Specs**: add "4.19 Requests over x402 (2026-10-04)" to `specs/proofmarket/implementation/en/01-requirements-definition.md`, and the endpoint to chapter 05 (API design).

## Do not touch
- The existing API-key request flow (`POST /v1/verifications`).
- Production env vars, DB and Vercel. Test with PGlite and the fake chain.

## Done when
- Tests: no payment → 402 with correct requirements / valid payment → request created and API key returned / wrong amount, wrong destination, wrong mint, fee payer abuse, reused payment → all rejected. Replace sending with the fake chain (follow `test/support/chain.ts`).
- The sample agent really paid and created a request on Devnet (local `pnpm dev:local` uses the fake chain, so it is fine to report that the real Devnet transaction will be checked by the owner's first session after release).
- The README's "Finishing" is satisfied and the PR is merged.
