# ProofMarket full audit (2026-10-08)

A look at the state right after the seven distinctive features (PRs #4–#11) landed on main and program v1.1 went onto devnet. The reader is the owner. The goal is to separate "fix before the hackathon submission (10/12)" from "fix before usage grows".

## Conclusion

All automated checks pass, and all seven features are live in production. The code's foundation (authentication, double-payment prevention, RLS, settlement retries) is solid. What needs fixing is not flaws in money or safety but **operational fragility and being hard to discover from outside**. Four things are worth doing before submission, about half a day together.

1. If any one step of the per-minute `tick` throws, the remaining steps (deadlines, claim expiry) stop too
2. There is no `robots.txt`, `sitemap.xml` or `llms.txt`, so machines cannot find a product built for agents
3. No CSP or frame-ancestors (next.config's "tighten in PR-05" was never done)
4. The README still says "7" MCP tools (there are 8)

One gap bears directly on revenue. Requirement 01 §4.1, "the fee is 0 but a field to record it is prepared", is implemented neither in the DB nor in the Solana program. The day fees are charged, a migration will be needed. How revenue should work is written separately in `docs/pitch/08-revenue-model.md`.

## How this was checked

Against main `1eb48df`: (1) ran the checks above locally; (2) read through authentication (`lib/auth/*`), rate limiting, `challenge-service`, `bounty`, refund targets in `task-engine`, double-payment prevention in `x402-service`, the tick in `jobs.ts`, `retention.ts`, the public surfaces in `public-service`/`map-service`, and `next.config.ts`; (3) sent GET to 9 URLs on production `https://proofmarket.fun` and looked at status codes and response headers (no authenticated operations were called); (4) for legal matters, only checked what `specs/proofmarket/legal-checklist.md` and 08 §7 say, with no legal judgement.

## What is done well (no change needed)

API keys look up the row by prefix and compare the secret part by SHA-256 hash in constant time. The admin token and cron secret use the same comparison, and OAuth requires PKCE. x402 payments are made exclusive in the DB with the signature as primary key, so even with several servers no payment creates two requests. A test watches that RLS is enabled on every public table. Settlement jobs retry with exponential backoff and drop to DEAD at the limit or deadline, from where `requeue` brings them back. There is no risk of a dispute's re-check flowing into result reuse (`reuse`) and rewriting someone else's request, because reuse only runs when the requester specifies it explicitly. G's decision to replace the brief's salt (the public `task_id_hash`) with an HMAC was also right.

## What to fix

### Before submission (half a day)

The most fragile part is the per-minute `tick` (`apps/web/lib/services/jobs.ts` from line 141). It simply calls `releaseStaleReviews` → `runOptimistic` → deadlines → claim expiry → job execution in order without catching exceptions in between. If, say, one challenge fails on a DB constraint, deadline processing for every request stops every minute until that one is fixed. Wrap each step in `try/catch`, record failures with `console.error` and in the return value, and move on.

`/robots.txt` and `/sitemap.xml` are 404, so neither search engines nor agents are guided. There is also no `llms.txt` for agents to read directly (MCP URL, OpenAPI, the x402 entry point and pricing on one page). Next.js's `app/robots.ts`, `app/sitemap.ts` and `public/llms.txt` are enough.

Responses carry neither CSP nor frame-ancestors (`apps/web/next.config.ts`). Today there are only `nosniff`, `Referrer-Policy` and `Permissions-Policy`, with nothing equivalent to `X-Frame-Options`. Privy's origins are known now, so `frame-ancestors 'none'` and a minimal CSP can be added. Worker screens use the camera and microphone, so `Permissions-Policy` also needs `microphone=(self)` (check on a real device that D's "speak to type" is not refused in production).

README's "Seven tools" should be 8 (`request_reality_verifications_batch` was added).

### Before usage grows (1–2 weeks)

`retention.ts` deletes only evidence and location observations; other tables keep growing. `rate_limit_counters` gains a row per key × 1-minute window, and expired `idempotency` and OAuth rows remain. Add a daily cleanup step to the tick.

The public dataset stops at 1,000 rows with no paging (`publicDataset(limit = 1000)` in `map-service.ts`). If chapter 06 names "AI training data" as a market, nothing can start without `since`/`cursor`.

The tick has one more problem: no cap on how much it does. `maxDuration = 300` seconds, but it is called every minute, so 60 seconds is the practical budget. At a few hundred requests a day, deadline processing will pile up. It needs a per-run cap (e.g. 200) and a return value saying it could not finish.

AI checking works only while this Mac is running. Production's `external_review_enabled` assumes launchd's `review-runner` judges with `claude -p` every 2 minutes. If the Mac stops, submissions wait 30 minutes in CHECKING and pass with a warning (PR #49). The design switches to in-server checks once `ANTHROPIC_API_KEY` is set, so decide when to switch together with a cost estimate.

There is also no way to learn that something broke: no exception collection (Sentry etc.) and no notification of DEAD jobs. The minimum is to include the DEAD count and failed steps in the tick's return value, and have `/v1/health` report "did a tick run in the last 5 minutes". A Vercel cron or an external uptime monitor watching that is enough.

A smaller point: only OAuth's `/oauth/token` has no rate limit (`authorize` and `register` do). PKCE keeps brute force harmless, but they should match.

The home page is `force-dynamic` to split languages by header, so it is rendered on the server every time. Making ja/en separate static routes or adding `revalidate` removes the 2.7-second first load.

### Dependency vulnerabilities (not urgent)

All 10 are transitive and not on server paths. Six are in Privy's browser-side wallet connection (`wagmi` → `@walletconnect` → `ws`, `uuid`, `decode-uri-component`) and four in the Solana SDKs (`@solana/spl-token` → `bigint-buffer`, `@anchor-lang/core` → `toml`, `jayson` → `stream-json`). `ws` and `uuid` can be raised with `pnpm.overrides`. `bigint-buffer` has no upstream fix; the whole ecosystem carries it.

### Gaps between spec and implementation

There is no fee field. 01 §4.1 says "the platform fee is 0 in the MVP, with only a field to record it", but neither `schema.ts` nor Solana's `Task` has a fee field. The program's `treasury` is the account for prepaid balances the operator holds, not a receptacle for fees. The day a rate is added, both a DB migration and program v1.2 will be needed.

Legal item D-05 also remains open. How the Payment Services Act treats a design where the operator holds prepaid balances and escrow is undecided (`legal-checklist.md` §3, 08 §7). It holds up because this is a trial (devnet, not redeemable). The shape of monetization has to be worked backwards from this constraint; chapter 08 covers it.

## Limits

Behaviour on a real device (iPhone Safari) was not checked. No load test was run, so the "as requests grow" assessments above are estimates read from the structure. The legal notes transcribe the checklist and do not replace expert review. The production admin API (DEAD job list) was not called, so the current number of DEAD jobs is unknown.
