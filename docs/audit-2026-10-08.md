# ProofMarket 全体監査（2026-10-08）

尖った機能 7 本（PR #4〜#11）が main に入り、プログラム v1.1 を devnet に載せた直後の状態を調べた。読者はオーナー。目的は「ハッカソン提出（10/12）までに直すもの」と「利用が増える前に直すもの」を分けること。

## 結論

機械的な検査はすべて通り、本番は 7 本とも配信されている。コードの土台（認証・二重払い防止・RLS・決済の再試行）は固い。直すべき点は、お金や安全の欠陥ではなく **運用の壊れやすさと、外から見つけにくいこと** に集まっている。提出前に手を入れる価値があるのは次の 4 つで、合わせて半日で収まる。

1. 毎分の定期処理 `tick` が、1 段でも例外を投げると残りの段（締切・クレーム失効）まで止まる
2. `robots.txt`・`sitemap.xml`・`llms.txt` が無く、エージェント向け製品なのに機械が見つけられない
3. CSP と frame-ancestors が無い（next.config の「PR-05 で締める」が未実施のまま）
4. README の MCP ツール数が「7 本」のまま（実際は 8 本）

収益化に直結するずれも 1 つある。要件 01 §4.1 の「手数料は 0 だが記録の欄は用意する」が、DB にも Solana プログラムにも実装されていない。手数料を取る日が来たら移行が要る。収益の考え方そのものは `docs/pitch/08-revenue-model.md` に分けて書いた。

## よくできている点（直さなくてよい）

API キーは接頭辞で行を引き、秘密部分は SHA-256 のハッシュと定数時間比較で照合している。管理者トークンと cron の秘密も同じ比較で、OAuth は PKCE 必須。x402 の支払いは署名を主キーに DB で排他しているので、サーバーが複数台でも二重に依頼は作られない。public の全表で RLS が有効なことはテストが見張っている。決済ジョブは指数バックオフで再試行し、上限か締切で DEAD に落として `requeue` で戻せる。異議の再確認が結果の再利用（`reuse`）に流れて他人の依頼を書き換える心配も、再利用が依頼側の明示指定でしか動かないので無い。G が指示書の salt（公開値 `task_id_hash`）を HMAC に替えた判断も正しい。

## 直す点

### 提出前（半日）

いちばん壊れやすいのは毎分の定期処理 `tick`（`apps/web/lib/services/jobs.ts` 141 行〜）だ。`releaseStaleReviews` → `runOptimistic` → 締切 → クレーム失効 → ジョブ実行、を順に呼ぶだけで、途中の例外を受け止めていない。たとえば異議の処理が DB の制約で 1 件落ちると、その 1 件が直るまで全依頼の締切処理が毎分止まる。各段を `try/catch` で包み、失敗を `console.error` と戻り値に残して次へ進む形にする。

`/robots.txt` と `/sitemap.xml` は 404 で、検索エンジンにもエージェントにも案内が無い。エージェントに直接読ませる `llms.txt`（MCP の URL・OpenAPI・x402 の入口・料金を 1 枚に）も無い。Next.js の `app/robots.ts`・`app/sitemap.ts` と `public/llms.txt` で済む。

応答ヘッダーには CSP も frame-ancestors も無い（`apps/web/next.config.ts`）。いまは `nosniff`・`Referrer-Policy`・`Permissions-Policy` だけで、`X-Frame-Options` 相当も無い。Privy のオリジンは今は分かっているので、`frame-ancestors 'none'` と最小の CSP を足せる。worker 画面はカメラとマイクを使うので `Permissions-Policy` に `microphone=(self)` も要る（D の「話して入力」が本番で拒まれていないか、実機で確かめること）。

README の「Seven tools」は 8 本（`request_reality_verifications_batch` が増えた）。

### 利用が増える前（1〜2 週間）

`retention.ts` は証拠と位置観測しか消さず、ほかの表は増え続ける。`rate_limit_counters` は鍵×1 分の窓ごとに行が増え、`idempotency` と OAuth の期限切れ行も残る。日次で消す段を tick に足す。

公開データセットは 1,000 件で切れ、ページ送りが無い（`map-service.ts` の `publicDataset(limit = 1000)`）。06 章で「AI の学習データ」を売り先に挙げているなら、`since`/`cursor` を足さないと始まらない。

tick にはもう 1 つ、件数の上限が無い問題がある。`maxDuration = 300` 秒だが、1 分ごとに呼ばれるので実質 60 秒が目安。依頼が 1 日数百件になると締切の処理が溜まる。1 回の上限（例 200 件）と、処理し切れなかったことを返す戻り値が要る。

AI 照合はこの Mac が動いている間だけ働く。本番の `external_review_enabled` は、launchd の `review-runner` が 2 分ごとに `claude -p` で判定する前提。Mac が止まると提出は CHECKING で 30 分待ち、warning で通る（PR #49）。`ANTHROPIC_API_KEY` を入れればサーバー内判定に切り替わる設計なので、費用の見立てと一緒に切り替え時期を決める。

壊れたことを知る手段も無い。例外の収集（Sentry 等）も、DEAD ジョブの通知も無い。最小限は、tick の戻り値に DEAD 件数と失敗段を含め、`/v1/health` が「直近 5 分に tick が走ったか」を返すようにする。Vercel の cron か外部の死活監視がそれを見れば足りる。

細かい点では、OAuth の `/oauth/token` だけレート制限が無い（`authorize` と `register` にはある）。PKCE があるので総当たりの実害は小さいが、揃えておく。

トップページは言語をヘッダーで分けるために `force-dynamic` で、毎回サーバーで描いている。ja/en を別ルートで静的化するか、`revalidate` を入れると初回 2.7 秒が消える。

### 依存の脆弱性（急がない）

10 件すべてが推移的依存で、サーバーの経路では使われない。6 件は Privy のブラウザ側ウォレット接続（`wagmi` → `@walletconnect` → `ws`・`uuid`・`decode-uri-component`）、4 件は Solana SDK（`@solana/spl-token` → `bigint-buffer`、`@anchor-lang/core` → `toml`、`jayson` → `stream-json`）。`ws` と `uuid` は `pnpm.overrides` で上げられる。`bigint-buffer` は上流に修正が無く、業界全体が抱えている。

### 仕様と実装のずれ

手数料の欄が無い。01 §4.1 は「プラットフォーム手数料は MVP では 0 とし、記録の欄だけ用意する」と書くが、`schema.ts` にも Solana の `Task` にも fee の欄は無い。プログラムの `treasury` は運営が預かる前払い残高の口座で、手数料の受け皿ではない。料率を乗せる日には、DB 移行とプログラム v1.2 の両方が要る。

法務の D-05 も未解決のままだ。前払い残高と escrow を運営が預かる設計は、資金決済法上の扱いが決まっていない（`legal-checklist.md` §3、08 §7）。試験運用（devnet、換金不可）だから成り立っている。収益化の形はこの制約から逆算する必要があり、08 章で扱う。

## 限界

実機（iPhone Safari）での動作は見ていない。負荷試験はしていないので、上の「依頼が増えると」の見立ては構造から読んだ推定。法律の記述はチェックリストの転記で、専門家の確認を代替しない。本番の管理 API（DEAD ジョブ一覧）は呼んでいないので、いま DEAD が何件あるかは分からない。
