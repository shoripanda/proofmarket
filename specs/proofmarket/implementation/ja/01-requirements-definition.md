# 01. 要件定義書

作成日: 2026-10-02

## 1. 目的と到達点

AI エージェントが「この店はいま営業しているか」を REST API で尋ね、実在の人間が現地で撮った写真と位置から判定された JSON の答えを受け取り、その確定と報酬の支払いが Solana Devnet に残る。これを 10/12 の提出時点で、実際の人間と実際の店舗で動かす。

提出時に満たす水準は `mvp-plan.md` のフォールバック水準に合わせる。

| 水準 | 内容 | 扱い |
|---|---|---|
| Level A | REST、worker 1 人、現地写真、ジオフェンス、nonce、Devnet の記録、構造化された結果 | 必達。これを壊す作業はしない |
| Level B | MCP、複数 witness と quorum、類似画像の検出、Webhook | 10/8 までに入れる目標 |
| Level C | x402 V2、worker の評判、複数地域 | 余裕があれば |

## 2. 範囲

### 対象

- タスク種別 `PLACE_STATUS_VERIFICATION` の 1 種類
- 回答の選択肢 `OPEN | CLOSED | UNCLEAR`
- 証拠: 写真 1 枚以上、位置、時刻、タスクに紐づく nonce
- Devnet 上のエスクロー（資金拘束）、結果の記録（attestation）、支払いと返金
- worker 用のスマートフォン向け Web アプリ（ネイティブアプリは作らない）
- requester 用の REST API、P1 で MCP サーバーと Webhook
- 審査員と第三者向けの公開結果ページ（写真は出さない）
- デモ用エージェント（REST を呼び、結果で次の行動を分岐する小さなスクリプト）

### 対象外

`requirements.md` 6 節の対象外に加えて、次も作らない。

- requester 向けの管理画面（API と公開結果ページで足りる）
- 運営者向けの管理画面（管理 API とスクリプトで代える）
- Mainnet での実資金の運用（`legal-checklist.md` の確認が済むまで機能ごと無効）
- worker の評判スコアの算出（記録だけは残す）

## 3. ロール

| ロール | 実体 | 認証 | できること |
|---|---|---|---|
| Requester | AI エージェント、またはその開発者 | API キー（Bearer） | 検証依頼の作成・取得・キャンセル、証拠画像の取得（P1） |
| Responsible Principal | requester に責任を持つ人または法人 | なし（API キー発行時に紐づける） | 運営者が API キーを発行するときの責任主体 |
| Worker | 招待された人間の witness | Privy のログイン（メールまたは Google） | タスクの閲覧・引受・撮影・提出・放棄、支払い履歴の閲覧 |
| Operator | プラットフォーム運営者 | 管理用トークン | requester・worker の停止、新規タスクの凍結、決済の停止、API キーの失効、証拠の公開停止 |
| Verifier | サーバー内の判定処理 | なし（内部） | 証拠の判定、合意の算出、オンチェーンへの確定 |
| Public viewer | 審査員・第三者 | なし | 公開結果ページと Solana Explorer の閲覧 |

API キーは必ず 1 つの Responsible Principal に紐づく（`users-and-stakeholders.md` 3 節）。責任主体のない API キーは発行しない。

## 4. 曖昧点の決定

既存仕様が決めていなかった運用ルールを以下に定める。worker への公平さと、エージェントが結果だけを見て分岐できることの二つを基準にした。

### 4.1 報酬額

`bounty.amount` は witness 1 人あたりの報酬額とする。作成時に `amount × required_witnesses` を requester の残高から引き当て、オンチェーンのエスクローに入れる。プラットフォーム手数料は MVP では 0 とし、記録の欄だけ用意する（`verification_requests.platform_fee_amount`、移行 0027。料率は `project-brief.md` のとおり未確定）。

### 4.2 支払いの対象

判定（07 章）をすべて通った提出を valid と呼ぶ。valid な提出をした worker には、回答が多数派かどうか、タスクが合意に至ったかどうかに関係なく 1 人分の報酬を払う。判定に落ちた提出には払わない。

理由は二つある。正直に UNCLEAR と答えた人や少数意見の人に払わないと、多数派に合わせる動機が生まれて検証の意味が薄れる。また worker は条件を満たす作業を終えている（`legal-checklist.md` 1 節の報酬・拒否ルールの明示に対応）。

### 4.3 合意の算出

- valid な提出が `required_witnesses` 件そろった時点、または deadline の時点で合意を算出する
- 最多の回答が `quorum` 件以上あり、かつ最多が 1 つに決まれば VERIFIED。回答はその値
- それ以外は REJECTED（理由 `NO_CONSENSUS`）
- deadline の時点で valid が `quorum` 件に届かなければ EXPIRED（理由 `INSUFFICIENT_WITNESSES`）
- UNCLEAR はほかの回答と同じ一つの値として数える。UNCLEAR が quorum を満たせば「VERIFIED / UNCLEAR」として返す
- `quorum` 件に達した時点での早期確定は MVP ではしない（向かっている途中の worker の扱いが決まっていないため。P2）

`required_witnesses = quorum = 1` が既定値で、P0 はこの設定だけで成立する。

### 4.4 キャンセル

requester がキャンセルできるのは「進行中のクレームが 0 件、かつ valid な提出が 0 件」の間だけ。資金拘束前なら CANCELLED で終わり、拘束後なら CANCELLED を経て全額返金して REFUNDED になる。worker が現地に向かっている最中のキャンセルは受け付けない（`TASK_NOT_CANCELLABLE`）。

### 4.5 期限

| 項目 | 既定値 | 上下限 |
|---|---|---|
| deadline（作成時刻からの長さ） | 依頼ごとに指定 | 10 分以上 24 時間以内 |
| クレームの有効期間 | 30 分（deadline を超えない） | 設定値 |
| nonce の有効期間 | `freshness.max_age_seconds`（既定 300 秒） | 60〜900 秒 |
| 1 クレームあたりの提出試行 | 3 回 | 設定値 |

位置の精度不足など本人の責任でない理由で落ちたとき、worker はクレームの有効期間内なら新しい nonce を取ってやり直せる。完全一致の写真の再利用（replay）と、ほかの提出とほぼ同じ写真（near-duplicate、P1）は不正の疑いがあるため、その場でクレームを打ち切る。

### 4.6 1 人 1 票

同じ worker が同じタスクを引き受けられるのは 1 回だけ。やり直しは同じクレーム内の試行として扱い、witness の数には加えない（`offchain-data-model.md` 5 節）。

### 4.7 その他の決定

| 項目 | 決定 |
|---|---|
| 複数 witness の受付開始 | PR-14 が入るまで、環境変数 `MAX_WITNESSES=1` で `required_witnesses > 1` を 400 `VALIDATION_FAILED` で断る |
| replay の比較対象 | 前段の検査を通ったすべての提出の写真（INVALID になったものを含む）。アプリは撮り直しのたびに新しい写真を撮るので、同じバイト列が再び来るのは操作された場合に限られる |
| 日次上限の「1 日」 | 日本時間（Asia/Tokyo）の暦日 |
| 依頼を閲覧できる範囲 | 作成した API キーだけ。同じ principal の別キーからも見えない |
| 24 時間を過ぎた冪等キー | 作成 API は `verification_requests` の一意制約で引き続き重複を防ぐ。同じ本文なら既存の依頼を 200 で返し、違えば 409 `IDEMPOTENCY_KEY_CONFLICT` |
| Storage の制限 | bucket 自体に `file_size_limit = 8 MiB`、`allowed_mime_types = image/jpeg` を設定する。署名 URL は申告したサイズを強制しないため |
| 依頼できる場所 | どこでも（4.15 節）。場所を問わない種類は位置を省ける |

### 4.8 依頼の種類の追加（2026-10-04）

MVP の中心は `PLACE_STATUS_VERIFICATION` のまま変えない。同じ撮影・判定・決済の仕組みで確かめられ、店の外から見えることだけを問う種類を 2 つ足す。API キーの `allowed_task_types` で許可したものだけを受け付け、既定は従来どおり `PLACE_STATUS_VERIFICATION` だけにする。

| type | 問うこと | 回答 |
|---|---|---|
| `QUEUE_LENGTH` | 店の外に並んでいる人の数 | `NO_QUEUE`・`SHORT_QUEUE`（5 人くらいまで）・`LONG_QUEUE`（6 人以上）・`UNCLEAR` |
| `NOTICE_POSTED` | 質問で名指しした掲示（臨時休業のお知らせなど）が店頭に出ているか | `POSTED`・`NOT_POSTED`・`UNCLEAR` |

見送ったもの: 在庫の有無は店内に入る必要があり、撮影の決まり（店内に入らない）と両立しない。価格は選択肢で答えられない。混み具合は人を写すことが主になるため、写り込みの扱いを決めてから検討する。行列も人が写るので、worker には後ろから顔が写らないように撮るよう表示する。

### 4.9 結果の再利用（2026-10-04）

同じ店について少し前に確定した結果があれば、人を出さずにそれを返せるようにする。worker を何度も同じ店に向かわせず、依頼する側の費用と待ち時間を減らすため。

- 依頼の本文に `reuse: { "max_age_seconds": 60〜3600 }` を付けると、作成の前に再利用できる結果を探す
- 再利用の対象は、元の依頼者が `allow_reuse: true` を付けた依頼だけ（既定は false）。お金を払って得た結果を、本人の知らないうちに他人へ渡さないため
- 条件: 同じ登録店舗、同じ `type`、同じ回答の選択肢、結果が VERIFIED、確定から `max_age_seconds` 以内。`NOTICE_POSTED` は質問でどの掲示かが変わるので対象外
- 見つかれば 200 で `reused: true`、元の `verification_id`、公開結果（05 §4 と同じ項目）を返す。新しい依頼は作らず、残高も動かさない（試験運用中は無料）
- 見つからなければ、ふつうに依頼を作る

### 4.10 円での受け取り（2026-10-04、準備のみ）

ウォレットを使わない worker が参加しやすいよう、報酬を円で受け取れる道を用意したい。ただし本物のお金の支払いは、`legal-checklist.md` 3 節（資金の預かり・送金の扱い）と 7 節（源泉徴収・インボイス）が片付くまで始めない（README の Hard constraints）。いま作るのは次の 2 つだけにする。

- 明細の CSV: worker が月ごとの報酬の一覧を自分で書き出せる。日付（日本時間）・依頼 ID・金額・状態・取引の URL。後で税務の確認に使う
- 円での受け取りの希望: worker が「円で受け取りたい」と登録できる（`workers.yen_payout_interest_at`）。口座番号などは集めない。運営者は希望者の数を見て、準備ができたら先に案内する

円で払う段階では、支払いの代行を許可を持つ事業者に任せる形を第一候補にし、運営者が requester の資金を預かって払う形は避ける。

### 4.11 worker の信頼度（2026-10-04）

提出の記録から worker ごとの信頼度を決め、依頼する側が条件を付けられるようにする。点数は作らず、理由を説明できる 4 段階にする。

| 段階 | 条件（直近 90 日の記録） |
|---|---|
| restricted | 写真の使い回し（`EVIDENCE_REPLAYED`）かほぼ同じ写真（`EVIDENCE_NEAR_DUPLICATE`）で落ちた提出がある |
| new | valid な提出が 3 件未満 |
| trusted | valid な提出が 10 件以上、複数人の依頼での一致率が 90% 以上（比べられる依頼が 3 件以上） |
| standard | それ以外 |

- 一致率は、VERIFIED になった複数人の依頼で、自分の答えが確定した答えと同じだった割合。少数意見でも報酬は払う（4.2）ので、一致率は報酬には関係させない
- 依頼する側は `worker_requirements: { "min_tier": "standard" | "trusted" }` を付けられる。条件に届かない worker には一覧に出さず、クレームは 403 `WORKER_NOT_ELIGIBLE`
- restricted の worker は 1 人だけで確定する依頼（`required_witnesses = 1`）を受けられない。複数人で突き合わせる依頼は受けられる
- worker は自分の段階と理由を報酬の画面で見られる。納得できなければ運営者に申し立てられる（参加規約 5 節）

### 4.12 異議と再確認（2026-10-04）

結果に納得できない requester は、確定から 24 時間以内に 1 回だけ異議を出せる。異議を出すと、同じ場所・同じ種類・同じ質問の「再確認」の依頼が新しく作られる。

- `POST /v1/verifications/{id}/dispute`。本文は `reason`（500 字まで、任意）、`assurance`（既定は `{ "level": "standard" }`）、`deadline_minutes`（10〜1440、既定 60）
- 再確認はふつうの依頼として作る（残高・上限・ポリシー検査・資金拘束も同じ）。費用は異議を出した requester が持つ
- 元の依頼の worker への支払いは取り消さない。条件を満たした作業には払う（4.2）。誰かを自動で罰することもしない
- 元の依頼の GET に `recheck`（再確認の ID・状態・答え・元の答えと一致したか）を、再確認の GET に `recheck_of` を出す
- 再確認の答えが元と違ったら、元の依頼に関わった提出を運営者が見直せるよう audit_events に残す

### 4.13 店舗からの申告（2026-10-04）

登録店舗が自分で「今日は臨時休業」「通常どおり営業」と申告できるようにし、依頼する側に参考情報として渡す。

- 運営者が店舗ごとに秘密のリンク（`/store/<token>`）を発行して渡す。ログインは要らない。リンクはハッシュだけを保存し、運営者が止められる
- 申告は「本日臨時休業（CLOSED_TODAY）」か「通常どおり営業（OPEN_AS_USUAL）」と、有効期限（既定は当日の終わり、日本時間）。店舗のメモ（200 字まで）は運営者だけが見る
- 判定には使わない。結果は今までどおり現地の人の確認で決める。依頼の GET に `store_report`（申告の内容と時刻）を別の欄として付ける。`result_hash` には入れない
- worker には見せない。申告に引きずられず、見たままを答えてもらうため

### 4.14 requester 用の画面（2026-10-04）

API だけでは状況をつかみにくいので、requester が自分の API キーの様子をブラウザで見られる画面 `/console` を作る。

- ログインは API キーを 1 回貼るだけ。サーバーが確かめてから、JS から読めない Cookie（httpOnly・SameSite=Strict、12 時間）でセッションを持つ。API キーそのものはブラウザに残さない
- 見られるもの: キーの情報（接頭辞・上限・許可された種類・状態）、残高と今日使った額、最近の依頼、Webhook の配信の状態、定期確認
- できる操作は、定期確認を止めることとログアウトだけ。キーの発行や作り直しは運営者が行う
- POST は Origin がこのサイトと同じときだけ受け付ける

### 4.15 人の手が要る作業への拡張（2026-10-04）

オーナーの判断で、店の前の確認に限っていた範囲を広げる。目的は「AI が自分ではできない、体を使う作業を人に頼めること」で、写真による確認はその一例にあたる。本や紙の資料を読む、実物を確かめる、電話で聞く、といった作業も頼めるようにする。安全のための決まりは、この節では新しく足さない（オーナーの指示）。既存の禁止語の検査はそのまま残す。

**依頼の種類（17 種類）**

| 区分 | type | 答えの形 | 場所 |
|---|---|---|---|
| 現地・選択 | `PLACE_STATUS_VERIFICATION`・`QUEUE_LENGTH`・`NOTICE_POSTED`（従来） | 選択 | 必須 |
| 現地・選択 | `CROWD_LEVEL`（混み具合）・`SEAT_AVAILABILITY`（空席）・`PARKING_AVAILABILITY`（駐車場の空き）・`STOCK_CHECK`（在庫） | 選択 | 必須 |
| 現地・数値 | `PRICE_CHECK`（値段） | 数値 | 必須 |
| 現地・文章 | `SIGN_TRANSCRIPTION`（看板・掲示・メニューの書き起こし）・`SITE_REPORT`（現地の様子の報告） | 文章 | 必須 |
| どこでも | `DOCUMENT_TRANSCRIPTION`（本・紙資料の書き起こし）・`DOCUMENT_QA`（本・紙資料を読んで答える）・`PRODUCT_INSPECTION`（実物の確認）・`PHONE_INQUIRY`（電話での問い合わせ）・`CUSTOM_TASK`（その他の作業） | 文章 | 省略可 |
| どこでも | `MEASUREMENT`（計測） | 数値 | 省略可 |
| どこでも | `CUSTOM_CHOICE`（依頼者が選択肢を決める質問） | 選択（2〜6 個、各 40 字まで） | 省略可 |

種類ごとの定義の正本は `packages/core/src/domain/enums.ts` の `TASK_TYPE_SPECS`。新しく発行する API キーは全種類を使える。運営者は `set-task-types.ts` で絞れる。

**答えの形**

- `answer_schema` は `{ "type": "enum", "values": [...] }`・`{ "type": "number", "unit", "min", "max" }`・`{ "type": "text", "max_chars" }` のいずれか。種類ごとに決まった形しか受け付けない
- 数値は `1,280` のような書き方も受け付け、`1280` に直して保存する。範囲の外は `ANSWER_INVALID`
- 文章は前後の空白を落として保存する。上限は 4000 字

**場所**

- 登録店舗の許可リスト（REQ-X-T-104）と対象地域の矩形（REQ-X-T-101）による拒否をやめる。どこの位置でも依頼できる
- 位置が登録店舗から 30 m 以内なら、従来どおり `place_id` を記録する。結果の再利用（4.9 節）と店舗からの申告（4.13 節）は、`place_id` がある依頼でだけ働く
- 運営者が API キーに個別の矩形（`allowed_bbox`）を設定した場合は、その範囲の外を断る
- 場所を省いた依頼ではジオフェンスの検査をせず（`not_run`）、worker の位置も求めない。worker の一覧には距離に関係なく出る

**判定**

- 選択と数値は、従来の多数決（4.3 節）で決める。数値は書き方をそろえた後の一致で数える
- 文章は一字一句そろうことがまずないので、多数決をしない。有効な提出が `quorum` 件そろえば VERIFIED とし、全員の文章を結果の `answers` に古い順で返す
- 文章の本文は公開の evidence バンドルにも Solana の記録にも載せない。バンドルには各提出の文章の SHA-256 を入れ、結果の `answer` には最初の文章の SHA-256 を入れる。`answers` は result_hash の計算から外す（文章そのものは依頼者だけが見られる）
- 書き起こしや電話には時間がかかるため、`freshness.max_age_seconds` の上限を 3600 秒に広げる。質問文の上限も、書名やページを書けるよう 1000 字に広げる

### 4.16 AI による内容の確認（2026-10-04）

オーナーの指摘による。依頼したエージェントは自分では現地の作業ができないので、届いた写真と答えが依頼どおりかを自分で確かめられない。仕組みの側で中身まで確かめ、その判定を記録して返さなければ、結果を信用できない。そこで、提出ごとに Claude が写真と答えを依頼文と突き合わせる。

- 機械的な検査（合言葉・受付時間・写真の形式・使い回し・似た写真・位置）がすべて通った後に、`vision_consistency` として行う
- Claude に渡すもの: 依頼の種類、依頼文、答えの形、答え、EXIF を落とした縮小版の写真。モデルは既定で `claude-opus-5-5`（環境変数 `REVIEW_MODEL` で変えられる）
- 判定は 3 つ。`pass`（依頼どおり）は合格。`fail`（明らかに依頼と違う。例: 書き起こしを頼んだのに要約、頼んだ項目が欠けている、写真と答えが食い違う）は不合格で、理由を worker に見せる。worker は同じ引き受けの中でやり直せる（`EVIDENCE_MISMATCH`、試行は 3 回まで）。`uncertain`（写真がぼやけていて読めない、電話のように写真では確かめようがない）は `warning` 付きで合格にする
- Claude の API が落ちているときは worker を止めない。`warning`（`verdict: "unavailable"`）で合格にし、結果にその旨が出る
- 依頼者には、合格した提出ごとの判定・理由・写真に写っていたもの（`result.reviews`）を返す。判定の状態は `checks.vision_consistency` として result_hash と evidence バンドルに入る。理由の文章は依頼者だけが見られ、ハッシュの計算からは外す
- `ANTHROPIC_API_KEY` が設定されていなければ、この確認は行わない（`not_run`）

### 4.17 運営者の Mac の Claude Code による確認（2026-10-04）

オーナーの指示により、4.16 節の確認を API の契約なしで、オーナーが契約しているサブスクリプションの Claude Code で行う。サーバーからサブスクの認証は使えないため、確認はオーナーの Mac で動かす。

- フラグ `external_review_enabled` を ON にすると、機械的な検査をすべて通った提出は `CHECKING`（確認待ち）のまま止まる。worker の画面には「内容を確認しています」と出て、15 秒ごとに結果を取り直す。同じ引き受けで次の提出はできない（`REVIEW_PENDING`）
- オーナーの Mac では launchd が 2 分ごとに `scripts/review-runner.ts` を動かす。実行役は `GET /v1/admin/reviews` で確認待ちの提出（依頼文・答え・10 分だけ有効な縮小版写真の URL）を受け取り、`claude -p`（Read だけ許可、構造化出力）に判定させ、`POST /v1/admin/reviews/{submission_id}` で判定を返す。認証は運営者の管理用トークン
- 判定を受け取ったサーバーは、4.16 節と同じ規則で合否を決める（`fail` は `EVIDENCE_MISMATCH` で不合格・やり直し可、`uncertain` は `warning` で合格）
- 確認待ちの提出がある引き受けは、有効期限を過ぎても期限切れにしない。依頼の締め切りも、確認待ちになってから最大 30 分は待つ。それを過ぎて届いた判定は記録だけして数えない
- 確認待ちが 30 分を過ぎた提出は、4.16 節の「API が落ちているとき」と同じ扱いにする（`verdict: "unavailable"`、`warning` 付きで合格）。worker の済んだ仕事と依頼者の締め切りを、運営者の Mac が動いているかどうかに左右させないため（2026-10-06 変更。それまでは不成立にしていた）。依頼者には `result.reviews` と `checks.vision_consistency` で、内容の確認なしで通ったことが分かる
- Mac が止まっていると確認は遅れる。30 分を過ぎた提出は確認なしで通るので、止まっている間は 4.16 節の確認が効かない
- `ANTHROPIC_API_KEY` が設定されていれば 4.16 節のサーバー内の確認が優先され、提出は止めない

### 4.18 写真の複数枚化（2026-10-04）

これまでは1回の提出で写真1枚だけだった。「店の外観と値札」「本の表紙と本文のページ」のように、2枚以上そろって初めて確かめられる依頼がある。AI による内容の確認（4.16・4.17 節）も、写真が多いほど判断しやすい。そこで、1回の提出で写真を最大4枚まで送れるようにする。

- worker は写真ごとにアップロードを1つ作る。1つのチャレンジ（合言葉）で作れるアップロードは4つまで。5つ目は 400 `VALIDATION_FAILED`（`reason: "upload_limit"`）
- 提出の `evidence` は1〜4件。どれも同じ引き受け・同じチャレンジの PENDING のアップロードでなければならない。同じアップロードを2回並べると 400 `VALIDATION_FAILED`
- 写真ごとの検査（形式・使い回し・時間・似た写真）は全部の写真に行う。1枚でも落ちれば提出全体が不合格になり、理由はその写真のものを使う。`machine_details.photo` に何枚目か（1から数える）を残す。同じ写真を1回の提出に2枚入れた場合も、使い回しとして不合格になる
- 位置の検査は提出に1回だけ行う（位置は提出ごとに1つ）
- `evidence_objects` は写真ごとに1行。evidence バンドルの `evidence_sha256` には全部のハッシュを、送られた順に入れる
- 依頼者向けの `GET /v1/verifications/{id}/evidence` は全部の写真を返す。同じ worker の写真は同じ `witness_ref` で、送られた順に並ぶ
- AI による確認には全部の写真を渡す。外部の確認（4.17 節）の一覧は `image_urls` に全部の URL を返す。2 分ごとに動いている古い review-runner が止まらないよう、当面は1枚目の URL を `image_url` にも入れる
- 送られた順は、ID を同じプロセス内で単調に増える ULID にして保つ（DB の移行は要らない）

### 4.19 x402 での依頼（2026-10-04）

これまでは、運営者が API キーを手で発行しないと依頼を出せなかった。x402 を入れて、Solana のウォレットを持つエージェントなら、申し込みも契約もなしに USDC を払って依頼を出せるようにする。審査で問われる「ほかの AI にも組み込めるか」への答えになり、Solana を使う理由（エージェントが自分の鍵で少額を即時に払える）もはっきりする。

- 窓口は `POST /v1/x402/verifications`。本文は `POST /v1/verifications` と同じで、`principal_ref` だけ要らない（送られても無視する）。API キーと Idempotency-Key も要らない
- 支払いが付いていなければ、HTTP 402 と x402 v2 の `PAYMENT-REQUIRED` ヘッダーを返す。方式は `exact`、ネットワークは `solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1`（Devnet）、通貨は `BOUNTY_MINT`、額は `bounty.amount × required_witnesses`（最小単位）。宛先 `payTo` と手数料の支払者 `extra.feePayer` は、どちらも運営者の鍵（treasury の持ち主）
- 402 を返す前に、依頼の作成を一度試して取り消す（下見）。方針違反・締め切り・上限などで断られる依頼は、払う前に 400 などで断る。共有された結果を `reuse` で受け取れる場合は、支払いなしでその結果を返す
- `PAYMENT-SIGNATURE` が付いていれば、運営者自身が facilitator として検証する。検証は coinbase/x402 の `scheme_exact_svm.md` の MUST をすべて満たす。命令の並び（Compute Budget 2 つ、TransferChecked、任意で Memo か Lighthouse を 3 つまで）、手数料の支払者がどの命令の口座にも出てこないこと、Compute Unit の単価が 5 lamports 以下、送金先が `payTo` の ATA、mint と桁数、額が完全に一致すること。さらに、アドレス参照表・Token-2022・マルチシグ・ATA の作成は受け付けない（仕様より厳しくする分には許されている）
- 通ったら運営者の鍵で手数料の支払者として署名し、送って `confirmed` まで待つ。そのあとで依頼を作る。受け取った額は台帳に TOPUP として入れ、通常の作成（`createVerification`）がそこから RESERVE する。エスクローへの入金（FUND_TASK）はこれまでどおり別の取引で行う（`architecture.md` 6 節の「支払い」と「報酬のエスクロー」を分ける決まりに従う）
- 支払い元のウォレットごとに principal を 1 つ作る（表示名 `x402:<公開鍵の先頭 8 字>`）。API キーは支払いのたびに新しく発行し、レスポンスで一度だけ返す。そのキーで `GET /v1/verifications/{id}` を読む。キーの上限は 1 件 5 USDC・1 日 20 USDC・1 分 30 回
- 同じ支払い（手数料の支払者の署名＝取引 ID）で依頼が 2 件できないようにする。支払いは `x402_payments` に記録し、主キーを取引 ID にする。確定済みの支払いがもう一度届いたら、同じ verification_id を返す（API キーは返さない）。本文が違えば 409 `PAYMENT_ALREADY_USED`。送信中なら 409 `PAYMENT_IN_PROGRESS`。120 秒たっても送信中のままなら、止まったものとみなして送り直せる。送り直す前にチェーン上で取引の有無を確かめるので、二重に払わせることはない
- 送信に失敗したら依頼は作らず、402 と `PAYMENT-RESPONSE`（`success: false`）を返す。支払い後に依頼の作成が断られた場合（下見のあとでフラグが変わったなど）は、受け取った額を新しいキーの残高に残し、そのキーをエラーの details に入れて返す
- ウォレットは SOL を持たなくてよい。手数料は運営者が持つ。窓口は IP ごとに 1 分 30 回まで
- MCP の道具の説明に、この窓口を案内する一文を入れる。MCP 自体の支払い対応はしない
- 見本のエージェントは `scripts/x402-agent.ts`。402 を受け取り、取引を組んで署名し、送り直して結果を待つ。17 種類のどれでも出せる（2026-10-05）。答えの形は種類の決まり（`TASK_TYPE_SPECS`）から組み、種類ごとに見本の質問を持つ。種類を指定しなければ、場所の要らない `CUSTOM_TASK` を出す。場所が必須の種類で場所が無いとき、`CUSTOM_CHOICE` で選択肢が無いときは、送る前に止める。結果を待つ間の通信の失敗では止まらない。試験用の USDC は Circle の faucet か、運営者が `scripts/x402-fund-agent.ts` で treasury から送る

### 4.20 家からできる仕事（2026-10-05）

場所を問わない依頼（4.15 節の「どこでも」の 7 種類）は、外に出なくてもできる。外出しにくい人（高齢の人、子育てや介護で家を空けにくい人、体が不自由な人）が働けるよう、位置情報なしで使える入口を作る。これまでは、位置情報を許可しないと一覧そのものが見られなかった。

- worker の一覧に「近くで」と「家でできる」の 2 つの切り替えを置く。選んだほうは端末に覚える（サーバーには保存しない）
- 「家でできる」は、場所を省いた依頼だけを締め切りの近い順に出す。位置情報を求めず、サーバーにも位置を送らない（`GET /v1/worker/tasks?scope=anywhere`）
- 「近くで」で位置情報が使えないときは、エラーで止めずに「家でできる」へ案内する
- 通知は、地域を 1 つも選ばなくても登録できる。その場合は、場所を問わない依頼だけが届く
- 引き受け・撮影・提出・判定・報酬は、ほかの依頼と変えない。信頼度の段階（4.11 節）もそのまま働く
- 公開サイトの worker 向けページに、家からできる仕事の説明を載せる

### 4.21 人が確かめた証明のリンク（2026-10-05）

エージェントが利用者に答えるとき、「これは AI の推測ではなく、人が確かめた事実だ」と示せるようにする。利用者は、いつ・何人が・どう確かめたかを自分で見られる。

- 結果が出た依頼の `result.proof` に、公開の結果ページの URL（`url`）、バッジ画像の URL（`badge_url`）、そのまま貼れる Markdown（`markdown`）を入れる
- 公開の結果ページ（`/r/{id}`）を、技術に詳しくない人が読める形にする。上から順に、確かめたかどうか、何の確認か（依頼の種類）、答え、確かめた時刻と経過時間、確かめた人数、通った検査、Solana の記録
- バッジは `/r/{id}/badge.svg`。「人が確認」と答え・時刻を 1 行で示す。結果がまだ無ければ「確認中」と出す
- 公開するのは従来どおり、質問文・位置・写真・worker の情報を除いた項目だけ。依頼の種類（`type`）は新しく公開する。文章の答えの本文は出さず、「文章の答え（内容は依頼者だけが見られます）」と示す
- ページは検索エンジンに載せない（`noindex`）。ID を知っている人だけが見られる前提は変えない
- あわせて直す不具合: 公開の結果が、文章の答え（`answers`）と AI の確認の記録（`reviews`）を返していた。どちらも依頼者だけが見られる決まり（4.15・4.16 節）なので、公開の結果から外す

### 4.22 確かめた事実のみんなの地図（2026-10-05）

「この駅のエレベーターは動いている」「この店は開いている」といった結果は、依頼した本人のほかにも役に立つ。依頼者が許した結果を、誰でも無料で見られる地図に載せる。1 件の依頼の結果が、車いすの人やベビーカーの人など、同じ場所へ行くほかの人の助けになる。

- 依頼の本文に `publish: true` を付けると、結果が VERIFIED になったとき公開の地図に載る。既定は false。お金を払って得た結果と自分の書いた質問文を、本人の知らないうちに公開しないため
- 公開するのは、質問文・依頼の場所（依頼者が指定した緯度経度）・登録店舗ならその名前・依頼の種類・答え・確かめた時刻・人数。写真、worker の情報、worker の正確な位置は公開しない
- 付けられるのは、場所のある依頼で、答えが選択か数値のものだけ。場所の無い依頼や文章で答える依頼に付けると 400 `VALIDATION_FAILED`（文章の答えは依頼者だけが見られる決まりのため）
- 地図に出すのは、確かめてから 72 時間以内の結果。古い事実を今のことのように見せないためで、各項目に確かめた時刻と経過時間を必ず添える。同じ場所・同じ種類・同じ質問の結果が複数あれば、新しいものだけを出す
- 画面は `/map`、API は `GET /v1/public/map`（認証なし、約 60 秒キャッシュ、最大 200 件）。公開の結果ページ（4.21 節）にも、公開を許した依頼では質問文と場所を出す
- 運営者が証拠へのアクセスを止めた依頼（`evidence_access_revoked`）は、地図にも結果ページの質問文にも出さない。削除の申し出（決まりのページ）を受けたときの止め方として使う
- `allow_reuse`（4.9 節）とは別の許可にする。再利用は「ほかの依頼者に結果を渡す」、公開は「誰でも見られる」で、範囲が違う

公開の可否とは別に、公開面に出す位置の細かさを `location_privacy` で選べる（13 §9 PR 7、2026-10-08）。既定の `"exact"` は依頼の緯度経度をそのまま出す。`"coarse"` にすると、結果ページ・地図・データセットでは geohash 6 桁の区画の中心（約 1.2 km × 0.6 km）に丸め、`location_precision_m: 1200` を添える。店名は場所を言い当ててしまうので出さない。地図では印の代わりに薄い円で描き、「おおよその場所（約 1 km）」と書く。依頼者の `GET` には正確な位置を返す。場所の無い依頼に `"coarse"` を付けると 400 `VALIDATION_FAILED`（`reason: "needs_location"`）。DB には丸めた値を持たず、出すときに計算する。

### 4.23 見守り依頼（2026-10-05）

「エレベーターが復旧したら知らせて」「棚に入荷したら知らせて」のように、答えが望む値になるまで確かめ続け、なったら止まって知らせる依頼。何度も見に行ったり問い合わせたりする手間を、依頼する側からもなくす。定期確認（4.14 節・04 §3.23）の拡張として作り、1 回ごとの依頼・残高・支払いは変えない。

- 定期確認に 2 つ目の回し方を足す。`every_minutes`（15〜1440 分おき）。従来の `times_jst`・`days_jst` とどちらか一方を指定する
- `max_runs`（1〜200 回）で回数の上限を決められる。上限に達したら止まる（`stopped_reason: "max_runs"`）。使ったぶんだけ払う仕組みは変えない
- `stop_when` で止める条件を決める。`{ "answer": "OPEN" }`・`{ "answer_in": ["OPEN", "UNCLEAR"] }`（選択の依頼）、`{ "number": { "min": 1 } }`・`{ "number": { "max": 300 } }`（数値の依頼）。文章の依頼には付けられない。選択肢に無い値は 400
- 条件は、作られた依頼の結果が VERIFIED になったときに調べる（tick ごと、1 分以内）。合えば定期確認を止め、`stopped_reason: "condition_met"` と `matched_verification_id` を記録する。合わなければ次の回を待つ
- 知らせ方は、合った依頼の `verification.verified` の Webhook と、定期確認の一覧（`GET /v1/schedules`）の `stopped_reason`。新しい Webhook の種類は足さない
- MCP に 3 つのツールを足す: `watch_reality_verification`（見守りの開始）、`list_reality_verification_watches`（一覧）、`stop_reality_verification_watch`（停止）。見守りも定期確認も同じ表なので、一覧には両方が出る
- 1 つの API キーで同時に動かせる定期確認の上限（10 件）は変えない

### 4.24 人が確かめた実世界データの公開（2026-10-07）

公開を許された結果（4.22 節の `publish: true`）は、地図に 72 時間載せるだけでなく、機械が読める形で誰でも取り出せるようにする。AI や Physical AI の学習・評価に使える「人が現地で確かめ、時刻と場所が付き、Solana に記録された観測」の集まりとして外に出すため。1 件の有料の依頼が、地図の先でも役に立つ。

- `GET /v1/public/dataset`（JSON、最大 1000 件、新しい順）と `GET /v1/public/dataset.jsonl`（1 行 1 件）。認証なし。約 60 秒キャッシュ
- 1 件に入れるもの: 依頼の種類、質問文、答え（選択・数値）、場所（依頼者が指定した緯度経度）、登録店舗ならその名前、確かめた人数、確定時刻、証拠のハッシュ（`evidence_root`）、結果のハッシュ（`result_hash`）、Solana の取引（署名・Explorer の URL）、証明のページの URL
- 入れないもの: 写真、文章の答え、worker の情報、worker の位置。地図と同じ
- 期間の制限はしない（地図の 72 時間はその場の案内のため。データは古くても観測として価値がある）。運営者が証拠へのアクセスを止めた依頼は外す
- 利用条件は CC BY 4.0（出典として ProofMarket と証明の URL を示す）。画面 `/data` に条件と取り出し方を書く

### 4.25 依頼者が仕事の形を決める（2026-10-08）

オーナーの指摘を受けた拡張。これまで依頼の「内容」（質問文）は自由だったが、「形」はこちらで決めていた。答えは 1 件に 1 つ、締切は 24 時間以内、場所は 1 地点、合格の条件を伝える欄は無く、同じ依頼を多くの場所へ一度に出す手段も無かった。この節で、形も依頼者が決められるようにする。17 種類は「今日すぐ頼める見本」の位置づけに下げ、主語は「エージェントに、人の体と五感を貸す」に置き直す（`docs/pitch/06-business-scale.md`）。安全の決まりは足さない（従来どおり）。

**1. 複数項目の答え（`answer_schema.type = "form"`）**

- 文章で答える種類（`SITE_REPORT`・`SIGN_TRANSCRIPTION`・`DOCUMENT_*`・`PRODUCT_INSPECTION`・`PHONE_INQUIRY`・`CUSTOM_TASK`）で、`{ "type": "form", "fields": [...] }` を受け付ける。項目は 1〜8 個。各項目は `key`（英小文字と数字と `_`、32 字まで）・`label`（80 字まで）・`type`（`enum`／`number`／`text`、形は単独の答えと同じ）・`required`（既定 true）
- worker の画面は項目ごとに入力欄を出す。答えは項目の順の JSON オブジェクト 1 つとして保存する（例 `{"open":"OPEN","price":1280,"note":"..."}`）。知らない鍵、必須の欠け、形に合わない値は `ANSWER_INVALID`
- 判定は文章の答えと同じ扱い（多数決をしない。有効な提出が `quorum` 件そろえば VERIFIED、全員分を `answers` に返す。公開バンドルと Solana には SHA-256 だけ）。DB の `answer_kind` は `text` のまま、`answer_spec` に `fields` を持つ。地図・公開データセットには載せない
- AI の照合（4.16 節）には答えの形として fields を渡す。項目の欠けは差し戻しの理由になる

**2. 合格の条件（`acceptance_criteria`）**

- 依頼に 500 字までの `acceptance_criteria` を付けられる。「値札が読める写真であること」「店名が写っていること」「要約でなく書いてあるとおりに」など、依頼者が受け取る条件
- worker には依頼の詳細と撮影画面で質問文の下に出す。Claude の照合には `<acceptance_criteria>` として質問文の隣に渡す（質問文と同じく信用しない入力として扱う）。GET の応答にも返す

**3. 場所を問わない仕事の締切**

- 場所を省いた依頼は、締切を今から 7 日（168 時間）後まで置ける。現地の依頼は従来どおり 24 時間以内。本を取り寄せる、電話が通じる時間を待つ、といった仕事のため
- クレームの 30 分と受付時間（`freshness`）は変えない。締切が遠くても、着手してからの流れは同じ

**4. 一括依頼（`POST /v1/verifications/batch`）**

- `template`（通常の依頼本文から `question` と `location` を省いたもの）と `items`（1〜50 件。各件に `location`・`question` のどちらか、または両方）を受け取り、件ごとに template に重ねて通常の依頼として検査・作成する。小売の棚の監査（同じ質問を 50 店舗へ）や AI 用データの収集（同じ場所へ違う質問）のため
- 全件通るか、1 件も作らないか（同じトランザクション）。失敗の応答には何件目かを `details.index` で返す
- 冪等キーは 1 つ受け取り、件ごとに `#<番号>` を付けて従来の冪等性の仕組みに乗せる。残高・1 日の上限・1 件の上限は合計で見る（15〜17 の検査は件ごとに積み上がる）
- MCP は `request_reality_verifications_batch`。SDK は `createVerificationBatch`

**見送ったもの（この節では足さない）**

- 写真なしの提出（電話の依頼など）: 位置・時刻・使い回しの検査が写真を前提にしており、外すと確かめる手立てが無くなる。別の節で設計する
- 手足を貸す仕事（受け取る・渡す・その場にいる）: 状態遷移と時間に応じた報酬が要る。`docs/pitch/06-business-scale.md` の「変えること 4」

### 4.26 尖った機能と初心者の導線（2026-10-08）

競合の調査（`docs/pitch/07-landscape-and-edge.md`）を受けて、他社に無い 7 つの機能と、文字に頼らない導線を足す。設計の正本は `13-edge-features.md`。急ぐほど上がる報酬（プログラム v1.1）、他のプログラムから読める事実、楽観的な確認（異議期間と保証金）、五感の指数、エージェントの行いの証明、worker 側のブラウザ内の助け（読み上げ・声で答える・音）、公開面の位置の丸め、サイトと worker アプリの「絵と音」の導線。DB の変更は移行 0023 の 1 回にまとめる。

### 4.27 判定を利用者に届ける（2026-10-09）

worker の提出が AI に確かめられ、答えが確定しても、依頼した AI エージェントが読みに来なければ、エージェントの利用者は何も知らない。「どうなった？」と聞いた人だけが判定を知る状態をなくす。

- `GET /v1/verifications/{id}` は `summary: { ja, en }` を返す。1 段落の人向けの文で、いまの状態（引き受け手を待つ・向かっている・AI が確かめ中 n 件・差し戻し n 件・仮の答え・確定・却下の理由・期限切れ）、答え、AI の照合の結果と理由、支払いの状態、証明のリンクを含む。`witness_progress` に `checking`（AI が確かめている提出数）と `returned`（依頼と合わず差し戻した提出数）を足す
- `GET` は `?wait=0〜45` を受け、状態が変わるか結果が出るまで最大その秒数だけ待ってから返す（長めのポーリング。レート制限は 1 回分）。MCP の `get_reality_verification` の `wait_seconds` も 45 秒まで。`request_reality_verification` にも `wait_seconds` を足し、作った直後の変化を待てる
- MCP のツールの説明と応答の `note` で、エージェントに「頼んだ直後に利用者へ伝える。利用者が待っている間は `wait_seconds=45` で呼び続け、`summary` が変わるたびに利用者に伝える。結果が出たら答え・AI の照合の判定と理由（`result.reviews`）・証明のリンクを聞かれる前に伝える」と指示する。エージェントの会話にサーバーから書き込む手段は MCP に無いので、ツールの説明で振る舞いを決める
- 受け入れ: `summary` は状態ごとに日英の文がテストで固定されている。`wait` は変化があれば直ちに返り、無ければ指定秒で返る。MCP の `request_reality_verification` は `wait_seconds` を付けると `verification`（`summary` 入り）を返す

### 4.28 API キーをその場で渡す（2026-10-09）

依頼者が `/join` で申し込んでも、運営者が手でキーを出すまで何もできなかった。メールを送る仕組みも無く、申し込んだ人には何も届かなかった。運営者の手が空くまで第三者が使い始められないのでは、外の人に使ってもらえない。申し込んだその場でキーを発行して画面に出し、エージェントへの設定まで済ませられるようにする。

- 依頼者の申し込みは、受けた時点で principal と API キーを作り、お試しの残高 5 USDC（Devnet の試験用。いつもの報酬 0.5 なら 10 件）を入れて、キーを応答で返す（`{ ok, delivery: "screen", api_key, principal_ref, trial_balance, emailed }`）。`principal_ref` は REST で依頼を作るときに本文に入れる ID（MCP では自動で入る）。画面はキーと `principal_ref`、Claude Code のコマンド・MCP の設定ファイル・REST の例を、キーを埋めた形で出す。キーが見えるのはこの 1 回だけで、DB にはハッシュしか残らない
- `RESEND_API_KEY` と `MAIL_FROM` があれば、同じ内容の控えをメールで送る（言語は申し込み画面の言語、既定は日本語）。送れなくてもキーは取り消さない（画面ですでに渡している）
- 乱用を抑えるため、同じ接続元（IP のハッシュ）からの発行は 1 日 3 つまで（UTC の日で数える。`rate_limit_counters` を日の窓で使う）。従来の 1 分 5 回もそのまま。IP は保存しない
- worker の申し込みは、これまでどおり運営者が招待コードを送る（`delivery: "operator"`）
- 申し込みの行には、小文字のアドレスの HMAC（`contact_hash`）と発行したキー（`credential_id`）を残す。運営者が申し込みとキーを突き合わせるため（移行 0026）
- 受け入れ: 返ったキーで認証でき、残高 5 が入っている。メールの送信に失敗してもキーは使える。同じ接続元からの 4 つ目はその日のうちは断られる。worker には従来どおりキーを出さない


## 5. 業務フロー

### 5.1 正常系（1 witness）

```text
Requester            ProofMarket API / Jobs              Worker (スマホ)           Solana Devnet
   | POST /v1/verifications ->|                              |                          |
   |<- 201 CREATED ------------|                              |                          |
   |                          |-- initialize_task ------------------------------------->|
   |                          |<- confirmed: FUNDED -> OPEN ----------------------------|
   |                          |<----- GET /v1/worker/tasks ---|                          |
   |                          |<----- POST claim -------------|                          |
   |                          |<----- POST challenge（現地）---|                          |
   |                          |--- nonce ------------------->|                          |
   |                          |<----- 写真アップロード・提出 --|                          |
   |                          | 判定 -> valid -> 合意 VERIFIED  |                          |
   |                          |-- finalize_verification + settle ---------------------->|
   |                          |<- finalized: SETTLED ----------------------------------|
   | GET /v1/verifications/{id} (ポーリング) または Webhook                                 |
   |<- VerificationResult -----|                              |                          |
```

### 5.2 主な異常系

| 事象 | 振る舞い |
|---|---|
| 誰も引き受けない | deadline で EXPIRED、全額返金して REFUNDED |
| 提出がジオフェンス外・鮮度切れ・nonce 不正 | 提出を INVALID にして理由を worker に見せる。試行回数が残っていればやり直せる |
| 写真の完全一致の再利用、ほぼ同じ写真 | 提出を INVALID、クレームを REJECTED。タスクは他の worker 向けに枠を戻す |
| RPC が落ちている | 結果は VERIFIED のまま settlement.status を PENDING にして、復旧するまで再試行を続ける。SETTLED とは名乗らない |
| Webhook の送信先が落ちている | ポーリングで結果を取れる。再送で決済が二重に起きることはない |
| 同じ Idempotency-Key で再送 | 1 回目と同じ応答を返す。中身が違えば 409 |

- Privy、Supabase、Vercel、Devnet 用 RPC（Helius など）の無料枠が使えること
